Le pattern ReAct (Reasoning + Acting) est l'architecture de référence pour les agents LLM qui doivent raisonner en plusieurs étapes avant de répondre. La plupart des implémentations passent par LangChain ou LlamaIndex. Dans **Audiomancy** — un assistant musical qui génère des tags pour des morceaux — j'ai choisi de l'implémenter directement, sans framework intermédiaire.

Voici pourquoi et comment.

---

## Le problème : générer des tags musicaux fiables

Audiomancy génère des tags Jamendo (genre, ambiance, instrument) à partir d'une description de morceau. Un simple appel LLM suffisait pour les cas simples, mais la qualité chutait sur les genres de niche — le modèle hallucine des tags inexistants ou trop génériques.

La solution : laisser l'agent chercher des informations réelles sur le web avant de répondre. D'où le pattern ReAct.

---

## La structure d'un agent ReAct

Un agent ReAct produit des blocs structurés en boucle :

```
Thought: [raisonnement sur ce qu'il faut faire]
Action: web_search
Action Input: [requête de recherche]
Observation: [résultat de l'outil]
Thought: [raisonnement sur l'observation]
...
Final Answer: [réponse finale]
```

L'implémentation complète tient en une classe Python de ~100 lignes :

```python
MAX_WEB_SEARCH = 3
MAX_ITERATIONS = 5

class AIAgent:
    def __init__(self, verbose: bool = True):
        self.verbose = verbose
        self.deepseek = DeepSeekClient()

    def run(self, prompt: str) -> str:
        scratchpad = f"Question: {prompt}\n"
        web_search_count = 0

        for iteration in range(MAX_ITERATIONS):
            llm_input = self._build_llm_input(prompt, scratchpad)
            response = self.deepseek.generate(llm_input)

            # Réponse finale détectée
            if "Final Answer:" in response:
                return filter_final_answer(response)

            # Appel d'outil : web_search
            if "Action: web_search" in response:
                if web_search_count >= MAX_WEB_SEARCH:
                    # Forcer la réponse finale
                    force_scratchpad = (
                        scratchpad + f"{response}\n"
                        + "Thought: I have used web_search 3 times. "
                          "I must now give the Final Answer.\n"
                    )
                    force_input = self._build_llm_input(prompt, force_scratchpad)
                    return filter_final_answer(self.deepseek.generate(force_input))

                query = self._extract_action_input(response)
                observation = web_search(query)
                scratchpad += f"{response}\nObservation: {observation}\n"
                web_search_count += 1
                continue

            # Réponse sans mots-clés structurels → traiter comme Final Answer
            if not any(kw in response for kw in
                       ("Thought:", "Action:", "Question:", "Observation:")):
                return filter_final_answer(f"Final Answer: {response}")

            scratchpad += f"{response}\n"

        return filter_final_answer(scratchpad)
```

Le `scratchpad` accumule tout l'historique de raisonnement et est réinjecté à chaque itération dans le prompt — c'est le mécanisme de mémoire de l'agent.

## L'outil web_search avec DuckDuckGo

Un seul outil suffit pour ce cas d'usage. La recherche DuckDuckGo (via `ddgs`) renvoie le premier résultat avec sa source :

```python
from ddgs import DDGS

def web_search(query: str) -> str:
    try:
        with DDGS() as ddgs:
            results = ddgs.text(query, max_results=1)
            for r in results:
                source = r.get("href", "unknown")
                text = r.get("body", "")
                return f"{text}\n\n(Source: {source})"
    except Exception:
        return "NO RESULT"
    return "NO RESULT"
```

La source est incluse dans l'observation pour que le LLM puisse citer d'où vient l'information — ce qui améliore la cohérence des tags générés.

## Le client DeepSeek avec métriques Prometheus

DeepSeek expose une API compatible OpenAI. Le client instrumente chaque appel avec des métriques Prometheus :

```python
from openai import OpenAI
from prometheus_client import Counter, Histogram

deepseek_requests_total = Counter(
    "deepseek_requests_total", "Total requests to DeepSeek API", ["status"]
)
deepseek_latency_seconds = Histogram(
    "deepseek_latency_seconds", "DeepSeek response time",
    buckets=[0.1, 0.5, 1.0, 2.0, 5.0, 10.0, 30.0]
)
deepseek_tokens_used = Counter(
    "deepseek_tokens_used", "Tokens consumed", ["type"]
)

class DeepSeekClient:
    def generate(self, prompt: str) -> str:
        start = time.time()
        try:
            response = self.client.chat.completions.create(
                model=self.model,
                messages=[{"role": "user", "content": prompt}],
                temperature=self.temperature,
                max_tokens=self.max_tokens,
                stop=["Observation:"],  # stoppe avant d'halluciner l'observation
            )
            deepseek_requests_total.labels(status="success").inc()
            deepseek_latency_seconds.observe(time.time() - start)

            if response.usage:
                deepseek_tokens_used.labels(type="total").inc(
                    response.usage.total_tokens or 0
                )

            return response.choices[0].message.content.strip()

        except Exception as exc:
            deepseek_requests_total.labels(status="error").inc()
            raise RuntimeError(f"DeepSeek API call failed: {exc}") from exc
```

Le `stop=["Observation:"]` est crucial : sans lui, le modèle génère lui-même les résultats de ses outils — c'est-à-dire qu'il hallucine les observations au lieu de laisser le code les fournir. En stoppant sur `"Observation:"`, on reprend la main exactement là où l'agent attend un résultat réel.

## Extraction robuste de la réponse finale

Les LLMs ne respectent pas toujours le format demandé. La fonction `filter_final_answer` gère les cas dégradés :

```python
def filter_final_answer(text: str) -> str:
    # Cas nominal : "Final Answer: tag1 tag2 tag3"
    for line in text.splitlines():
        if line.lower().strip().startswith("final answer:"):
            answer = line.split(":", 1)[1].strip()
            tags = answer.split()
            return " ".join(tags[:7])  # max 7 tags

    # Fallback : chercher la dernière ligne courte sans mots-clés ReAct
    for line in reversed(text.splitlines()):
        line = line.strip()
        if not line:
            continue
        if any(kw in line for kw in
               ("Thought:", "Action:", "Action Input:", "Observation:", "Final Answer:")):
            continue
        words = line.split()
        if 1 <= len(words) <= 7:
            return line

    return ""
```

La limite à 7 tags est métier : Jamendo affiche mal les listes de plus de 7 tags, donc l'agent est contraint dès l'extraction.

## Pourquoi pas LangChain ?

LangChain aurait fourni `AgentExecutor`, `Tool`, et des callbacks Prometheus prêts à l'emploi. J'ai choisi de ne pas l'utiliser pour deux raisons :

**Debugging plus simple.** La boucle ReAct custom est lisible en entier dans un fichier de 100 lignes. Quand l'agent boucle ou produit des tags incorrects, le `scratchpad` est directement loggé — pas besoin de comprendre les couches d'abstraction de LangChain pour voir ce qui se passe.

**Contrôle des cas limites.** Le cap à `MAX_WEB_SEARCH = 3` et la reprise en main forcée ("I must now give the Final Answer") sont des comportements difficiles à câbler proprement dans LangChain sans surcharger des méthodes internes. En custom, c'est 5 lignes.
